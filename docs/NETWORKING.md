# Сеть: почему локального bhop недостаточно

Если сервер авторитетен, он повторяет движение по входным командам и возвращает коррекцию при несовпадении. Клиентский эффект может выглядеть как телепорт назад, рывки или отключение. Причину устанавливают по логам/состоянию, а не по одному слову в окне.

Нужны согласованные:

1. Формула и конфигурация на сервере и predicted client: cap, acceleration, friction, scale, limiter.
2. Timestep/substep и порядок прыжка, friction, collision.
3. Сериализация нужного ввода/состояния и восстановление при replay.
4. Работа с авторитетным режимом, crouch, платформой, телепортом и респавном.
5. Отображение remote characters через обычную интерполяцию/репликацию игры.

В Unreal CMC используй saved moves и серверный replay, а не дополнительный локальный SetActorLocation. [Официальное устройство CMC](https://dev.epicgames.com/documentation/en-us/unreal-engine/understanding-networked-movement-in-the-character-movement-component-for-unreal-engine). В Unity и Godot конкретный networking stack проекта определяет authoritative tick, prediction и reconciliation; готовое решение из другого stack автоматически не переносится.

Проверка: сервер + минимум два реальных клиента; одинаковый seed/input replay, контроль конечной позиции и speed history; затем задержка/потеря пакетов и восстановление. Конкретные допуски должны соответствовать timestep и коллизиям игры. Standalone-примеры репозитория демонстрируют движение, а не готовую репликацию.

Для чужого сервера, чья симуляция не поддерживает этот movement, локальная правка не делает режим совместимым. Нужен поддерживаемый мод/серверный профиль, а не обещание универсального исправления DLL клиента.
