# От запроса до работающего bhop

## 1. Дай ИИ доступ к материалам

Лучший вариант — исходный проект игры. Если есть только установленная игра, укажи папку и известный способ моддинга. Если ассистент умеет только чат и не читает файлы, приложи исходный контроллер или выполняй его команды сам. Обещать автоматическую установку без доступа к файлам нельзя.

Скопируй стартовый запрос из README. Скажи, нужен ли `goldsrc-stock` или `classic-bhop`, удержание прыжка и UPS. Если не знаешь — начни с classic-bhop в отдельном локальном тесте.

## 2. Дождись конкретной диагностики

ИИ должен назвать путь контроллера/класса и функцию, которая применяет движение; ось вверх и единицы; текущую модель коллизий; источник ввода; режим одиночной/сетевой симуляции. Формулировка «похоже на Unity» без проверки недостаточна.

Пример полезного результата: «Godot 4, Player.gd, _physics_process, CharacterBody3D; скорость XZ в метрах/с; move_and_slide изменяет velocity; серверной симуляции в проекте нет». Для неизвестной сборки нужна дальнейшая проверка, а не придуманный адрес функции.

## 3. Выбери точку изменения

Для собственного проекта внедряй расчёт в существующий контроллер. Демо из examples — способ проверить механику на простой площадке, а не повод удалить игровой контроллер целиком. Для готовой игры сначала найди поддерживаемый loader/API, затем модифицируй нужный метод. Для закрытой неподдерживаемой сборки может потребоваться исследование, и результат не гарантирован.

## 4. Сохрани базовую скорость

Измерь обычный бег до изменения. Если v_world=7.5 и ты хочешь считать его 300 UPS, scale=300/7.5=40. Воздушный предел тогда 30/40=0.75 мировой единицы/с. Копирование 30 напрямую в Unity при скорости бега 7.5 даст огромный ошибочный стрейф.

Примерные world defaults в демо: Unity/Godot scale=40, Unreal scale=0.4 из-за сантиметров. Это выбранная согласованная калибровка, не требование движков.

## 5. Реализуй один шаг

Ввод → проверка разрешённого прыжка → при необходимости срез stock-bhop → наземное трение или воздушный режим → горизонтальный разгон → вертикальная физика → sweep/slide движка → измерение результата. Схема подробнее в ALGORITHM.md.

Прыжок должен срабатывать на первом разрешённом физическом шаге после приземления. Иногда это следующий tick, потому что grounded описывает предыдущий Move; такой порядок нужно учитывать, а не бесконечно принудительно ставить grounded=true.

## 6. Проведи проверки

Сначала `python tools/check.py`, затем язык своей реализации и игровую сцену по TESTING.md. Обязательны воздух без ввода, разгон A/D с поворотом, остановка после отпускания прыжка, 20 последовательных прыжков, стена, низкий потолок, респавн. Для сети — настоящий сервер и клиенты, а не два окна без проверки авторитета.

## 7. Получи установку и откат

ИИ должен назвать созданный мод/сборку и способ вернуть исходное состояние. У готовой игры хеш оригинала и проверка версии важнее красивого имени DLL. В отчёте должны быть фактически проведённые тесты; «должно работать» — описание ожидания.

## Как опубликовать этот набор

Создай пустой репозиторий на GitHub и загрузи содержимое корневой папки, включая docs, examples, reference, tests и tools. Не загружай .godot, bin, obj, временные компиляторы или игровые файлы. Название можно оставить HL1-Bhop-Everything. Проверь, что README находится в корне. Авторские примеры и текст имеют MIT-лицензию; внешние документы и SDK сохраняют собственные лицензии.
