# Instructions for the coding assistant

For a request to add bhop to a game, adapt the actual movement controller rather than assuming a universal patch. Read docs/START-HERE.md, then only the relevant engine guide. Follow the user's chosen location, bhop preset and existing authorization. For a task limited to this repository's documentation or examples, use the repository guidance below without inventing a target game or installation task.

1. Establish facts: project/game path, engine/version, architecture/runtime, source or mod access, actual player controller, physics update, input bindings, up axis, unit scale, and movement authority. Report an unknown as unknown. A file name is evidence, not proof of an engine or a compatible binary.
2. Find the single writer of locomotion velocity. Keep collision, moving platforms, animations and gravity under a coherent owner. Do not run a second movement controller beside the original. Prefer supported extension points or source edits over binary surgery.
3. Choose a small integration patch or the included standalone demo. Standalone controllers are teaching examples, not drop-in production replacements. Preserve game-specific jump eligibility, crouch clearance and other movement modes unless the task changes them.
4. Use docs/ALGORITHM.md and reference/goldsrc.py. C++ and C# ports consume GoldSrc units. Convert engine velocities and thresholds consistently. Air acceleration uses the full wishspeed after maxspeed, while the air projection cap is min(wishspeed,30). Never clamp the whole air velocity to 30 or reset it to wish velocity each frame.
5. Decide actual jump eligibility before ground friction. A held but blocked jump does not skip friction. Stock bunny limiting runs once on an accepted takeoff, not every airborne tick. The classic-bhop preset deliberately disables it.
6. Input sampling and physics may use different schedules. Latch discrete jump presses for a physics step, keep held state for auto-hop, and avoid a dt multiplier twice. Drive from the game's intended simulation timestep; do not introduce an arbitrary frame clamp as if it were a GoldSrc formula.
7. Build and compare the math against tests/cases.csv. Test the actual game's floor, wall, ceiling, stairs, jump sequence, crouch and death/respawn. A Python pass does not prove a Unity or Unreal component compiles. An engine compile does not prove a full match works.
8. In multiplayer use the same simulation on the authority and predicted client. Preserve replayable inputs/configuration. Do not claim a client-only velocity change makes a remote server support new movement. Replication work is part of that integration, not a reason to remove checks.
9. For compiled games read docs/COMPILED-GAMES.md: identify the exact build, preserve originals, verify expected bytes and provide a reversible installation. Never reuse a game's RVA in another game/version. This repository does not authorize unrelated proxy, account, protection or server changes.
10. Deliver changed files, build/install instructions, rollback and an evidence-based report. Separate measured behavior, inspection and unrun tests. If blocked by absent source, editor, loader or tools, state the concrete missing requirement and keep any completed work reviewable.

For this repository itself: keep public examples free of local user paths, personal logs, game binaries and inherited game-specific patches. New engine integrations need docs, test commands and a truthful validation status. See CONTRIBUTING.md.
